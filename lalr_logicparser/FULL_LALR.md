# Plan: Port All Missing Python Grammar Productions to Go LALR

## Context

The Go LALR grammar (`lalr_logicparser/grammar_v17.y`) currently covers ~28% of the Python grammar (`ivy_parser.py`). It has complete formula/term parsing, basic action parsing, scenario parsing, and proof/tactic parsing. What's missing is the entire **declaration-level grammar** — all the `top : ...` productions that define modules, types, schemas, actions, interpretations, etc.

This port will bring the LALR grammar to full parity with the Python grammar, enabling cross-validation of all Ivy language constructs.

## Files to Modify

| File | Changes |
|------|---------|
| `lalr_logicparser/grammar_v17.y` | Add ~45 new tokens, ~40 new nonterminals, ~200 new productions |
| `lalr_logicparser/lalr_parser.go` | Add ~45 new token mappings in `Lex()` switch |
| `lalr_logicparser/grammar_v17.go` | Regenerated by `goyacc` |

## Approach

Since all 102 needed AST types already exist in Go, the port is purely mechanical: translate each Python PLY production rule into a goyacc production with the corresponding Go AST constructor call. Only 5 minor AST types are missing (NamedSpace, ProductSpace, SumSpace, IncludeDecl, NativeAction) — these can use stub types or be skipped.

### Execution Strategy

The grammar will be built in sections, matching the Python file's organization. After each section, run `goyacc` to catch syntax errors early, then `go build` to catch type errors.

## Section 3: Top-Level Declaration Grammar

Transform `top` from a single-input parser to an accumulating declaration parser. Python uses `top : top DECL` for sequential declarations. In Go LALR, use a similar pattern but since our entry point needs to handle single inputs AND declaration sequences:

```yacc
top:
    fmla                { result = $1 }
    | sequence          { result = $1 }
    | scenario          { result = $1 }
    | TOK_TACTIC ...    { result = ... }
    | TOK_PROOF ...     { result = ... }
    // Single declarations (for cross-validation of individual decl parsing)
    | decl              { result = $1 }
    ;
```

Then `decl` handles all declaration forms.

4. `go vet ./lalr_logicparser/...`

## Key Design Decisions

1. **`top` nonterminal**: Rather than using `top : top DECL` (which requires parsing multiple declarations in sequence), use `top : decl` to parse a single declaration. This matches the cross-validation use case where we parse one construct at a time. The Python `top : top DECL` pattern is for file-level parsing which the hand-written parser handles.

2. **Actions in `decl`**: Keep the existing action grammar in `sequence`/`action`/`simpleact`/`complexact` as-is. Only add missing action variants.

3. **Missing AST types** (NamedSpace, ProductSpace, SumSpace): Use `ast.Atom` as a placeholder in the grammar actions, or skip concept-space `expr` productions entirely since they're rarely tested.

4. **NativeQuote**: The lexer handles NATIVEQUOTE specially (multi-line strings). The LALR parser can accept the token but semantic actions may be simplified.

5. **Version gates**: Only port v1.7+ productions since the grammar is `grammar_v17.y`.
