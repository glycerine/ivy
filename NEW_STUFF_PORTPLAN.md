## Integration procedure

- Keep the current branch and commit by feature cluster. Record upstream hashes and the tests run in each integration commit. Commit approximately every 15 minutes, preferably after `cd ~/ivy/goivy && make test` passes. Use Go commit subjects of at most 60 characters followed by a two- or three-sentence body. Use `test_vectors/` for Go fixtures.
- Compare the upstream base and tip with the tracked `pyivy/ivy/` subtree. Apply clean, self-contained changes under that prefix after checking their context. The repository layout differs, so a path-prefixed patch is usually simpler than a direct cherry-pick. For overlapping files, reconcile the smallest semantic hunks against local changes, then regenerate parser tables where required. Keep local source-location and XTrace behavior, Z3 and context ownership fixes, and fork-specific compiler behavior.
- The initial tree comparison found 26 overlapping runtime files under `ivy/`, including the checker, compiler, both parser paths, solver, isolate, actions, liveness, VMT, and C++ generator. Treat these as merge work. Most pure additions can be brought over with their upstream commit IDs. For files in the same feature cluster, review the final upstream implementation as well as the individual deltas so intermediate regressions do not become local features.
- Make the Go changes through existing command, library, desktop, and web entry points as appropriate. Keep grammars as version-specific syntax adapters and put AST construction and semantics in shared Go code. Regenerate all affected tables and test mixed-language-version compilations in one process.
- Use focused Python and Go fixtures to compare acceptance, proof outcome, effects, diagnostics, and output artifacts. Check positive, negative, and backwards-compatible behaviors. Use the existing fast Go suite and targeted upstream tool smoke tests. Leave the 16-hour Go golden tests out of this run.
