    ivy_check: derived invariants
    
    Add "derived invariants" (doc/projects/derived_invar.md): an invariant that is
    IMPLIED by the normal invariants, so it needs no consecution check -- only a
    one-state implication (assume the normal invariants, prove the derived one).
    Derived invariants are assumed in the pre-state of the normal invariants'
    consecution checks, so they serve as freely-usable supporting lemmas.
    
    Syntax: `derived invariant [name] <formula> {with ...} {using ...}`.
    
    Dependency rule: a derived invariant may depend at zero delay on all the normal
    invariants (implicitly) and on other derived invariants (via `with`/`using`); a
    NORMAL invariant may NOT depend on a derived one at zero delay (via `with`), as
    that closes a zero-delay cycle -- this is checked and reported as an error.
    
    Implementation:
      - ivy_ast: a `derived` flag on LabeledFormula (mirrors `explicit`).
      - ivy_parser: a `derived invariant ...` rule reusing the with/using clauses.
      - ivy_check: check_conjs_in_state gains a `derived` parameter that selects the
        normal set (consecution) or the derived set (implication), and raises an
        error on a normal->derived `with` dependency; a new derived pass checks the
        derived invariants by a one-state implication against get_conjs_normal (the
        normal invariants only, so a derived is not trivially self-assumed); the
        consecution pass runs only when there is a normal invariant.
    
    Tests (test/derived1..4): an implied derived passes; an unimplied one gives a
    counterexample; a normal-on-derived `with` errors; a derived-on-derived `with`
    and a normal `using` a derived both pass. Added to test/ivy_tests.py.

    ivy_check: `using` clause and `patdef` for choosing inductive hypotheses
    
    Add fine-grained control over which inductive hypotheses a consecution check
    uses (doc/projects/invariant_choice.md). By default every consecution check
    uses all available hypotheses; when consecution fails, unneeded hypotheses
    constrain the CTI and slow the solver. The user can now name a subset.
    
    Features:
      - `invariant [i] ... using pat` restricts invariant i's consecution check to
        the hypotheses whose names match the name-pattern `pat`. With no `using`
        clause the default is unchanged (use all).
      - `patdef name = pat` defines a named pattern, referenceable in later `using`
        clauses and patdefs (no forward references).
      - Pattern language: `|` (union), `-` (difference, binds tighter), `*`
        (wildcard for an arbitrary string), `$` (anchor at the root), parentheses.
        A leaf is matched against a hypothesis name anchored at any ancestor of the
        invariant's object, so `x` matches `x`, `a.x`, `a.b.x`, ... Name resolution
        qualifies exact leaves to their nearest-enclosing invariant and leaves
        wildcards raw.
    
    Implementation:
      - ivy_lexer: `patdef` keyword.
      - ivy_ast: PatDiff, UsingPat/UsingPatDecl, PatDef/PatDefDecl (PatDef.defines
        reports the pattern name so a duplicate patdef is caught as a redefinition).
      - ivy_parser: pattern grammar, `optusing` on the invariant rule, `patdef` top
        rule (one new shift/reduce, the greedy leaf munch, resolved as intended).
      - ivy_module: usingpats, patdefs maps.
      - ivy_compiler: usingpat/patdef handlers and expand_patrefs (eager expansion
        of pattern references).
      - ivy_check: get_conjs_gated gates each named hypothesis h in the pre-state
        with a fresh assertion literal (a_h -> h); each invariant's check is
        conditioned on the conjunction of the literals its pattern selects (all of
        them if it has no `using` clause). Engaged only when `using` clauses are
        present, so proofs without them are unaffected.
    
    Tests (test/): usingpat1..5 exercise selection, the |/-/* operators, patdef
    (chained and with difference), and `$`; patdef1..3 cover duplicate detection
    and object/module-scoped patdefs. All added to test/ivy_tests.py.

    Add Verilog-style bfe/concat sugar (ivy1.8+): a<<i:j>> and a::b
    
    Introduce two infix notations for bit-vector operations, since `bfe` and
    `concat` look unfamiliar to hardware designers:
    
      a<<i:j>>          desugars to  bfe[j][i](a)   (Verilog-style high:low
                                                     part-select; note the index
                                                     order is reversed vs bfe)
      a1 :: a2 :: ... :: an   desugars to  concat(a1, a2, ..., an)
    
    The lexer gains tokens for '<<', '>>' and '::' (all existing occurrences of
    these are inside <<<...>>> native-quote tokens, so nothing else is affected).
    The parser adds two rules, gated to language version 1.8 and later, that
    return the desugared bfe/concat application directly -- no new AST classes,
    and the rest of Ivy is unaware of the surface syntax. A chain of '::' flattens
    into a single variadic concat (parenthesized concats are left intact). As with
    plain `concat`, a concatenation still needs a sort annotation where its width
    cannot be inferred.
    
    Documents the sugar in basics.md and adds a regression test
    (bfe_concat_sugar.ivy) checking it emits the same RTL as the explicit
    bfe_concat.ivy.

Author: Kenneth McMillan <you@example.com>

    ivy: make concat variadic and interpret it only when widths add up
    
    Previously concat was fixed at two arguments, so a packed value had to be built
    with nested concats -- and Ivy could not infer the intermediate widths, forcing
    awkward workarounds (e.g. splitting a cache line into separate field arrays).
    concat is now variadic.
    
    - compile_app builds the concat application with a function sort of the right
      arity (fresh TopSorts); HM inference unifies each argument sort and leaves the
      result sort to context, exactly as for the binary case. So
      `concat(full, dirty, hi, data) : line` type-checks directly.
    - The polymorphic table's arity-2 template is unchanged; type_inference already
      uses the symbol's own (now arity-N) sort per occurrence.
    - Z3 encoding uses variadic z3.Concat; ivy_to_cpp emits an N-way shift/or fold;
      ivy_to_rtl already emitted a brace list, so it was already variadic.
    
    concat is added to the interpreted polymorphic symbols, but is encoded as z3's
    Concat only when it is *safe and meaningful*:
    - every argument sort and the result sort must be interpreted as a bit-vector;
      otherwise (e.g. inside an isolate that does not interpret one of the sorts)
      concat stays an uninterpreted function -- still sound by congruence. This also
      fixes a latent issue: previously binary concat was a single uninterpreted
      symbol regardless of its argument sorts; it now gets a per-signature name.
    - when all sorts are bit-vectors but the result width does not equal the sum of
      the argument widths, concat is likewise left uninterpreted and a warning is
      emitted (once per signature), rather than crashing z3 with a sort mismatch.
    
    Verified: the full normal suite (135 tests) and the hardware suite (check +
    to_rtl) pass; focused tests confirm all-bv concat round-trips through bfe,
    non-bv concat stays uninterpreted, and a width mismatch warns and stays
    uninterpreted.

    Add trace_dir= to save a counterexample for every failing check
    
    ivy_check gains a `trace_dir=<dir>` option: instead of stopping at the first
    failing check (as `trace=true`/`out=` do), it computes a counterexample for
    every failing check and writes each to <dir>/<name>.a2g, where <name> is the
    check's name (as used by check=). Each check is queried on its own so its trace
    is a genuine counterexample to that check; the first counterexample found for a
    given name is kept. The directory must not already exist and is created, so
    traces from a previous run are never overwritten.
    
    This supports tooling -- e.g. a Proof-General-style editor integration -- that
    annotates each failing property with its counterexample.
    
    Implementation reuses the existing trace-generation machinery (factored out as
    build_trace_handler): the trace_dir branch of check_fcs_in_state loops over the
    checks, builds a trace per failing one, and writes it, without exiting.
    Program-assertion checks are named via check_safety_in_state's new name
    argument. Checker.fail() now also retains the model under trace_dir, and
    build_trace_handler tolerates a null trace_hook (it is called more than once
    now). The out= and trace= behaviors are unchanged.

    Add check= option to select checks by name; fix assert= extension handling
    
    ivy_check gains a `check=pat,...,pat` option that restricts the checks
    performed (invariants, properties, program assertions) to those whose name
    matches one of the given glob-like patterns. A pattern matches as a substring
    of the fully-qualified check name (e.g. `cpu.invar12`); '.' is a literal dot
    (so `cpu.` selects the components of `cpu` but not `cpufoo`) and '?' matches
    any single character. Unselected checks are still assumed, just not verified --
    useful for focusing on one failing invariant while debugging.
    
    This generalizes the existing `assert=<file>:<lineno>` option, which selects a
    single check by source location. Both are implemented as filters that turn
    unselected checks into assumptions: the name filter (check_name_selected) is
    applied in AssertAction.action_update alongside the existing lineno filter, and
    in ivy_check when enumerating properties, conjectures and guarantees. The two
    filters are conjoined, so assert= continues to work as before.
    
    Also fix assert=: it silently checked nothing when the file name was given with
    its '.ivy' extension (it unconditionally appended '.ivy', producing a name that
    matched no source location). It now accepts the file name with or without the
    extension.

commit d5e30fb67a6470caddeae597b7d1d87deb2ccec0
Author: Kenneth McMillan <you@example.com>
Date:   Sat Jul 4 14:33:10 2026 -0700

    Fix two type/wire compiler bugs affecting the hardware models
    
    Sort ascriptions on applications were dropped by compile_app (except for
    numerals), so a polymorphic operator whose result sort is not determined by
    its arguments -- e.g. `bfe[i][j](x) : t` -- could not be sort-inferred even
    when the argument sort was known from context. Apply the ascription as a
    constraint on the compiled term: for an application, fix the range of the
    (possibly polymorphic) head symbol; for a bare constant, set its sort. HM
    inference then enforces it (and still catches a conflicting ascription).
    
    Wires were not frozen during actions when declared and defined separately
    (`wire x : t` + `definition x = e`). The `definition` handler unconditionally
    registered a DerivedUpdate, so a wire depending on a register would be threaded
    through sequential composition and read its post-update value (e.g.
    `pc := pc+1; ir := fetched` read fetched at the new pc). Skip the DerivedUpdate
    when the defined symbol is a wire, mirroring the inline `wire x = e` case.

    Add bfe/concat hardware example and enable the concat operator
    
    Add bfe_concat, a registered nibble-swapper that exercises the
    bit-field-extract and concat operators:
    
        out := old( concat(inp[3:0], inp[7:4]) )
    
    The combinational submodule swaps the two 4-bit halves of the input
    using bfe[0][3]/bfe[4][7] and concat, and a register latches the result.
    
    The concat operator was present in the solver's z3 mapping but was not
    recognized at the logic level, so it could not be used in Ivy source
    ('unknown symbol: concat'). Add it to polymorphic_symbols_list with
    independent argument/result sorts (like arrsel), so concat(bv[j],bv[k])
    elaborates to bv[j+k].
    
    The emitter already handled both operators (bfe as a sigspec slice,
    concat as a sigspec concatenation). The generated bfe_concat.il passes
    yosys read_rtlil/hierarchy/check and is proven sequentially equivalent
    (from reset) to a reference registered nibble-swap. The existing
    test_to_rtl and refinement3 outputs are unchanged.
